# 食光：代码分类与修改范围

核对日期：2026-09-25。固定网站：https://a1426424086-spec.github.io/

维护者负责公共内容和网站功能；使用者负责自己的食材、食谱和配餐。使用者在网页里保存的内容不会提交到 GitHub。维护者在普通网页中操作，也只修改自己的本机档案。

## 分类总表

| 分类 | 包含什么 | 谁来修改 | 修改后影响谁 |
| --- | --- | --- | --- |
| 01 公共内容 | 好物推荐、商品图、公开参考食谱 | 维护者修改文件并发布 | 公共列表；不自动覆盖已经保存的私人副本 |
| 02 默认资料 | 初始食材、默认份量、分类和蛋白折算规则 | 维护者修改源码、检查兼容后发布 | 新档案；已有档案是否更新取决于明确的版本迁移 |
| 03 个人数据 | 自建或修改的食材、导入的商品、私人食谱、日期配餐、本机档案 | 各使用者在网页内操作 | 当前设备、浏览器、网站、所选档案 |
| 04 网站功能 | 界面、计算、日期、保存、导入、交互 | 维护者修改源码、验证后发布 | 所有加载新版本的人；修改须保护已有个人数据 |
| 05 旧版代码 | 旧 Sites / ChatGPT 登录、D1 接口与数据库定义 | 技术维护 | 当前 GitHub Pages 页面未使用，不代表已经有云备份 |

本次按职责标注文件、建立查找入口，现有文件位置和运行逻辑保留。分类名称不是新建的运行目录，也不是新增的访问权限系统。

## 01 公共内容：日常更新主要改这里

“源码路径”相对于本机 `nutrition-app/`；“仓库路径”相对于 GitHub 发布仓库根目录。

| 内容 | 源码路径 | GitHub 仓库路径 | 可以改什么 |
| --- | --- | --- | --- |
| 好物推荐 | `public/content/recommendations.json` | `content/recommendations.json` | 名称、分类、链接、截图路径、日期、每100克碳水/包装蛋白/脂肪、折算比例、每份重量与单位 |
| 商品截图 | `public/recommendations/` | `recommendations/` | 增加或替换图片；换图用新文件名，避免旧缓存 |
| 公开参考食谱 | `public/content/recipes.json` | `content/recipes.json` | 名称、所属组、三餐及加餐的原料和克数、菜式说明、食材营养 |
| 网站图标 | `public/favicon.svg` | `favicon.svg` | 网站图标 |

同一商品修改时保留 `id`。推荐按更新时间倒序，同一天按文件顺序；参考食谱的分组和碳水排序由组件决定，不是仅靠 JSON 数组顺序。

```text
维护者修改公共 JSON / 图片 → 发布到固定 GitHub Pages 网站
    ├─ 好物：lib/recommendations.ts → components/recommendations.tsx
    └─ 参考食谱：lib/recipe-templates.ts → components/recipe-templates.tsx
```

对应板块打开、手动刷新、页面重新可见/聚焦、重新联网及可见时每60秒会尝试读取。发布、缓存或网络失败可能延迟显示。只修改本机源码、尚未发布，其他人不会看到。

完整格式见[好物推荐更新说明](好物推荐更新说明.md)，源码与发布仓库均放在 `docs/` 下。

## 02 默认资料：与每个人的食材库分开

| 源码路径 | 作用 | 修改边界 |
| --- | --- | --- |
| `lib/foods.json` | 初始食材清单、营养与份量 | 修改它不等于直接修改别人手机里的食材库；发布前检查迁移策略 |
| `lib/nutrition.ts` | 初始食材、分类、餐次、默认折算、热量和营养计算 | 默认值和通用计算共同使用；改公式会影响重新计算的结果 |
| `lib/catalog-previous.json`、`lib/catalog-draft-previous.json`、`lib/catalog-calibration-previous.json` | 识别旧版默认食材的对照资料 | 用于兼容，不是三个待展示的食材库，不要当重复数据删除 |

当前 `lib/device-storage.ts` 的 `migrate()` 只在旧版本标记满足条件时执行迁移，不是每次刷新重置全部食材。目录迁移按旧身份和数值识别默认项，也包含旧名称与份量调整；蛋白规则版本迁移会更新个人食材库及今天/未来的配餐，过去配餐与已存食谱快照保留。

因此不能承诺“改默认数据永远不会影响任何现有配餐”。以后新增迁移须明确作用范围，并验证用户修改过的数据。

## 03 使用者自定义：实际记录不在仓库中

实际记录保存在使用者浏览器的 `localStorage`。代码文件规定读写方式，本身不含对方的记录。

| 个人内容 | 数据字段 / 入口 | 用户可以做什么 |
| --- | --- | --- |
| 自己的食材库 | `DeviceData.foods`；`saveDeviceFood` / `deleteDeviceFood` | 新增、改名称/营养/份量单位/折算比例、删除 |
| 我的食谱 | `DeviceData.recipes`；`saveDeviceRecipe` / `deleteDeviceRecipe` | 改名称、增删食材、改克数、保存或删除；含公开模板的私人副本 |
| 日期配餐 | `DeviceData.days`、`draft`、`draftDate`；`saveDeviceDay` | 给不同日期安排三餐及加餐、改用量、按日期套用食谱 |
| 旧版存储兼容 | `lib/local-profiles.ts` | 保留旧版已选中的记录位置；网站不再提供生成、命名或切换档案入口 |
| 未保存的食谱编辑 | `lib/recipe-draft.ts`、页面内存状态 | 保存后才进入私人食谱；未保存就关闭可能丢失 |

| 源码路径 | 职责 |
| --- | --- |
| `lib/device-storage.ts` | 个人数据结构、读取、写入、校验、版本迁移 |
| `lib/local-profiles.ts` | 本机档案代码和存储键 |
| `lib/recipe-draft.ts` | 食谱私人副本与编辑草稿 |
| `lib/recommendation-import.ts` | 把公共商品复制到本机食材库，不反向发布 |
| `components/local-profile-panel.tsx` | 旧版页面，当前不再引用或打包 |

存储键保持兼容：

```text
shiguang-device-v1                 原有个人档案
shiguang-device-v1:SG-…            各专属码对应的个人档案
shiguang-profiles-v1               本机档案列表
shiguang-active-profile-v1         当前/上次使用档案
```

当前没有云端备份、跨设备同步或维护者查看他人记录的功能。不要把真实用户的个人备份放进公开仓库。

## 公共内容变成私人副本后

| 操作 | 当前程序的结果 |
| --- | --- |
| 用户导入好物 | 把当时食品和营养复制到自己的食材库 |
| 维护者随后修改或下架好物 | 公共列表更新；已导入的本机食品不被覆盖或删除 |
| 用户再次导入同一 ID 或同名食品 | 提示已经存在，不覆盖用户改过的值 |
| 用户修改公开参考食谱并保存 | 生成私人副本，公共原版不变 |
| 维护者修改公开参考食谱 | 公共原版更新，已存私人副本不自动改写 |
| 用户修改自己的食材营养 | 自己食材库及今天/未来含该食材的日期配餐更新；过去配餐和已存食谱快照不变 |
| 用户把私人食谱用于某日期 | 优先使用自己当前库中的同 ID 食材，缺失时使用快照；新配餐数值可能与旧食谱不同 |
| 用户把公开参考食谱用于某日期 | 使用该模板的食材值；目标日期已有配餐时须确认替换 |
| 用户删除食材库中的食材 | 只删库中条目；已有日期配餐和私人食谱的食材快照保留 |

“公共列表”“个人食材库”“日期配餐”和“食谱快照”是不同数据，不是同一份实时共享记录。

## 04 网站功能：改源码后重新构建

| 源码路径 | 职责 |
| --- | --- |
| `app/page.tsx` | 页面切换、配餐、编辑、日期套用、保存和删除；连接公共读取和本机读写 |
| `app/globals.css`、`app/layout.tsx` | 手机布局、字体、配色、导航、站点标题 |
| `components/recommendations.tsx` | 好物卡片、图片链接、导入按钮 |
| `components/recipe-templates.tsx` | 参考食谱展示、分组、排序 |
| `components/food-quantity.tsx` | 克/个/根/份等输入与换算 |
| `lib/recommendation-model.ts` | 好物字段校验、推荐营养转个人食材 |
| `lib/recommendation-feed.ts` | 公共内容刷新、读取失败处理 |
| `lib/validation.ts`、`lib/dates.ts` | 输入校验和日期处理 |
| `components/ui/`、`hooks/`、`lib/utils.ts` | 通用组件和辅助方法，不保存个人配餐 |
| `scripts/`、构建配置、依赖文件 | 内容检查、开发和构建 |

GitHub 仓库当前主要保存部署产物，源码位于本机 `nutrition-app` 和源码备份包。仓库中的 `assets/app.*.js`、`assets/app.*.css` 是生成文件，不手改压缩代码。功能修改应回到源码，再构建发布；保留旧哈希资源和存储键，保护已打开的页面和个人记录。

## 05 旧版保留：不是正在使用的云后台

`app/api/foods/route.ts`、`app/api/recipes/route.ts`、`app/chatgpt-auth.ts`、`lib/api.ts`、`lib/storage.ts`、`db/`、`drizzle/` 是旧 Sites / D1 方案的接口和资料。`examples/d1/` 是示例，`.openai/hosting.json` 是旧站点配置。

当前 GitHub Pages 是静态应用，前端未调用上述个人数据接口。保留这些文件不表示腾讯云已经接通，不表示记录写进 GitHub，也不表示当前网站需要 ChatGPT 登录。它们不是日常内容编辑入口。

## 修改与发布的边界

1. 改好物/参考食谱，先读远端最新文件，再同步源码，避免旧本机副本覆盖已发布的编辑。
2. 校验营养、引用 ID、图片路径；同一食品不要为改名字随意换 ID。
3. 改功能、默认资料或迁移时，验证已有自定义食品、私人食谱、历史配餐和档案隔离。
4. 发布到原仓库、原网址，核对发布成功和公开文件一致性。
5. 个人数据不作为公开内容示例。当前页面没有“备份/恢复”按钮；底层 `parseBackup` / `restoreDevice` 不等于已经提供操作入口，云端保存也尚未接入。
